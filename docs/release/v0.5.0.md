# rpc-io v0.5.0

Bounds on three things a peer could make rpc-io hold without limit. They were
found by an independent review of 0.4.0. Upgrading needs no code change unless
a peer sends ids over 1 KiB, LSP batches, or more than 32 connections from one
address; each is a setting.

## Request ids are bounded

An id was bounded only by the string budget, and each deferred request in
flight keeps copies of its id until it is answered. `Limits::max_id_bytes`
now caps an id's JSON text: 1 KiB by default, 256 B under `Limits::network()`
and 128 B under `Limits::strict()`. A request with a longer id is refused with
`-32600` under a `null` id before the id is copied anywhere, and its handler
does not run. A response with a longer id matches none of ours.

## Answers held for a batch are bounded

A batch is answered as one array, so while one member is deferred, the answers
to the others wait. Nothing bounded those bytes. `Config::max_batch_bytes`
(16 MiB) now does, over all open batches:

- an answer that would go past it is replaced by a short `overloaded_code`
  error under its own id;
- a batch that arrives while the budget is spent, or while a batch with such
  a replaced answer is still open, is refused whole with one `overloaded_code`
  error under `null`, and none of its members is handled.

`Limits::lsp()`, and so `Config::lsp()`, now turns batches off: LSP has none.

## A `Server` slot cannot be held by trickling bytes

After a connection's first message, any bytes restarted its idle clock,
including a blank line that forms no message, so one byte per idle period held
the slot forever. Only a whole message, or our own traffic, counts as activity
now.

A client that sends a real message every idle period keeps its connection, as
any client may. So one peer IP address may now have at most
`max_connections_per_address` connections open (32 by default, set with
`Server::with_max_connections_per_address`). One more is closed as soon as it
is accepted, and the accept loop carries on. Behind a proxy every connection
has the proxy's address: raise or remove the limit there. This does not stop
many addresses, so an internet-facing `Server` still needs a connection limiter
in front of it, and a TLS front end for any credential sent in an opening
request.

## Also fixed

A malformed message that reused the id of a request still being answered was
answered under that id. The peer saw two answers for one id, and with a gate
the error was taken as the opening request's failure. It is now refused under
`null`, as a valid duplicate already was.

## Compatibility

MSRV 1.85, as before. The new fields are on `#[non_exhaustive]` structs, so
adding them is not breaking. Behaviour changes: ids over 1 KiB are refused,
`Limits::lsp()` refuses batches, and a `Server` refuses a 33rd connection from
one address.
