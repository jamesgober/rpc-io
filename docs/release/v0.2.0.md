# rpc-io v0.2.0 — The JSON-RPC 2.0 Foundation

**The foundation release.** v0.2.0 turns the scaffold into a working JSON-RPC
2.0 engine: Content-Length and newline framings over `Read`/`Write`, the
envelope model, batches, id correlation, cancellation in both directions, and
an opening-request gate, built on the family's own `jsonx-lib` with no
third-party runtime dependencies. Register handlers on a `Router`, hand it a
byte stream, and every request gets exactly one response with the error codes
the specification prescribes, whatever the peer sends.

## What is rpc-io?

The JSON-RPC 2.0 transport of the LexerSketch servers, in the owner's
net-collection. LSP (lsp-lang 2.0, Wave M, decision D25), MCP (mcp-io), and
the Studio backend speak JSON-RPC 2.0 over one of two framings. rpc-io owns
that layer once (framing, the envelope, correlation, cancellation plumbing,
and the robustness fixes) and leaves method semantics to the protocol crates
above it. (Corrected in 0.3.0: this paragraph first listed DAP among them;
DAP shares the Content-Length framing, but its messages are not JSON-RPC.)

## What's new in 0.2.0

### A server in one call

```rust
use jsonx_lib::json;
use rpc_io::{End, ErrorObject, Framing, Router};

let router = Router::new()
    .request("add", |_, params, _| {
        let p = params.parse()?;
        match (p[0].as_i64(), p[1].as_i64()) {
            (Some(a), Some(b)) => Ok(json!(a + b)),
            _ => Err(ErrorObject::invalid_params("expected [a, b]")),
        }
    })
    .notification("exit", |_, _, cx| cx.stop());

let input: &[u8] = b"{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"add\",\"params\":[2,3]}\n\
                     {\"jsonrpc\":\"2.0\",\"method\":\"exit\"}\n";
assert_eq!(rpc_io::serve(input, std::io::sink(), Framing::Newline, router)?, End::Stopped);
# Ok::<(), rpc_io::Error>(())
```

### Framing

`Framing::ContentLength` (LSP, DAP) and `Framing::Newline` (MCP stdio, JSON
Lines), with `encode` and a sans-IO `Decoder`. The decoder holds at most one
message plus an 8 KiB read chunk however the peer sends: a body's buffer grows
as its bytes arrive, never from the header's word alone; an oversized message
is skipped as it arrives and reported (`FrameError::TooLarge`, recoverable);
line-end searches run eight bytes at a time and resume where they stopped.
Content-Length overflow, duplicates, missing headers, and header lines that are
not `token: value` are precise, final errors.

### Messages

`decode` reads a body in one pass of `jsonx-lib`'s pull reader. `params`,
`result`, and error `data` stay borrowed `Raw` slices of the body (validated
once, parsed only if a handler asks), and method names and string ids borrow
when they have no escapes. Malformed bodies become an `Invalid` that knows the
right answer: `-32700` for invalid JSON, `-32600` for a bad envelope, under the
message's own id when it has a `method` and a valid, unrepeated id, and never
for a broken response.

### The endpoint

`Endpoint` is one connection, both ways: it routes the peer's requests and
notifications to a `Router`'s handlers (answered now, or later through a
`Responder` that can move to a worker), and settles answers to our own
requests, sent through a `Peer` from any thread and awaited on a `Call`.
`Config` sets the limits, the pending-request capacity (oldest evicted),
deadlines, the cancellation spelling (`Cancellation::lsp()` or `mcp()`), and a
`Gate` for protocols with an opening request (LSP's and MCP's `initialize`,
LexerSketch's `auth`).

- **Exactly one response.** A deferred request dropped without an answer is
  answered `INTERNAL_ERROR`; a cancelled one is answered `-32800` (LSP) or not
  at all (MCP), and a late answer returns `Error::AlreadyAnswered`.
- **Panics contained.** Handler, event-hook, and sink panics are caught; the
  request is answered `INTERNAL_ERROR` and the session goes on.
- **Batches** are answered as one array, one response per request, sent when
  the last deferred answer arrives; nothing for a batch of notifications.

### Examples

`stdio_echo` (a stdio server, newline or `--content-length`) and `pipe_pair`
(a client and a server over an in-memory pipe: concurrent requests, a deferred
answer with progress, a cancelled request).

## Adversarial review

The 0.2 work in progress had been written by an earlier session, unreviewed and
partly uncompiled. It was finished and then reviewed adversarially; each
finding got a failing test before its fix (`tests/adversarial.rs`):

| Severity | Finding | Fix |
|---|---|---|
| Medium | A header line whose name is not an HTTP token (a body that ran into the next header) was skipped as an unknown header, silently losing a message and resynchronizing on a wrong boundary. | `FrameError::InvalidHeader`. |
| Medium | A repeated `id` behind another repeated envelope member was trusted: the error went out under one of two conflicting ids. Found by the classification property. | Repeats of `id` tracked on their own; answered under `null`. |
| Medium | An opening request cancelled under a cancellation with no reply (MCP) left the gate half-open forever: every later request was refused. | The gate shuts again; a new opening request is served. |
| Medium | A panicking `Sink` unwound through the endpoint, or through a worker that was sending. | Caught; closes the connection as an I/O error. |
| Medium | A message sent from a worker while a handler ran was not flushed until the handler returned. | Flushed at once when sent from another thread. |
| Low | An "answer" to a request still held behind the gate settled it, though the peer had never seen it. | Treated as unmatched. |
| Medium | Newline framing judged a line split across reads by its length, but a whole line by its blankness first: an over-long whitespace-only line was skipped or refused depending on read sizes, and an oversized line's `length` was `None` or `Some` the same way. Found by the chunking property on Linux. | Every line counts against the limit, blank or not; newline framing always reports `length: None`. |
| Low | Held-request lookups scanned every held message: `O(n·m)` for a peer flooding forged answers. | Indexed; `O(log n)`. |

The decoder also did not compile (a moved range), and several doc examples
dropped the endpoint they used.

## Dependency wiring

`jsonx-lib` 0.2 is the only dependency (`default-features = false`; `std`
forwards to `jsonx-lib/std`). No `-lang` crate is wired: method semantics
belong to the protocol crates above. Typed params and results through
jsonx-lib's `ToJson`/`FromJson` move to v0.5.0: those traits arrive in
jsonx-lib 0.5 (D25), a release this crate cannot make. Deferred replies,
listed for v0.5.0, were delivered here because cancellation needs them. The
moves are recorded in `dev/ROADMAP.md`.

## Breaking changes

**None.** v0.1.0 had no public API. The release profile no longer sets
`panic = "abort"`, which would have made handler-panic containment impossible
in this crate's own examples.
