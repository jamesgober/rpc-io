# rpc-io v0.4.0 — Typed JSON, and MCP as It Is Now

**The typed release.** v0.4.0 moves rpc-io onto jsonx-lib 0.5 and makes its
`ToJson` / `FromJson` traits the primary typed API: params decoded straight
from the message (borrowing where the type does), results written straight
into a buffer the endpoint reuses. It brings the MCP preset up to the
protocol's current, stateless revision (2026-07-28), enforces MCP's progress
rules, and makes the 1.0 decisions now, so that 1.0 can be a freeze. The
default build still depends on jsonx-lib alone, now re-exported as
`rpc_io::jsonx`.

## What is rpc-io?

The JSON-RPC 2.0 transport in the owner's net-collection: framing, the
envelope, correlation, cancellation, and the robustness fixes, once, for the
servers above it. lsp-lang 2.0 runs on rpc-io 0.2; mcp-io 0.2 is being built
on this release. Method semantics belong to those protocol crates. DAP shares
only the Content-Length framing.

## What's new in 0.4.0

### Typed params and results through jsonx-lib's traits

jsonx-lib 0.5's `FromJson` and `ToJson` are hand-written traits (no derive,
no reflection, no third-party dependency), and they are now rpc-io's typed
API, in every build:

- `Router::request_json` decodes a handler's params into `P` (answering
  `-32602` with the path and byte offset of what did not fit, without calling
  the handler) and encodes its `ToJson` result straight into a buffer the
  endpoint reuses: no `Value` is built and, once the buffer has grown,
  nothing is allocated for the result. `Router::request_encoded` does the
  encoding half for a handler that takes its params as they come, which is
  the way to decode params that borrow from the message (`Params::decode`).
- `Router::notification_json`, `Raw::decode`, and `Call::wait_json` decode;
  `Peer::notify_json`, `Peer::request_json` (and the same on `Context`),
  `Responder::ok_json`, and `Notifier::notify_json` encode in a per-thread
  reused buffer, outside the endpoint's lock.
- Decoding uses the endpoint's JSON budgets and refuses repeated keys.

The `serde` feature stays, as the alternative for crates written against
serde (`lsp-types`, MCP schema crates).

```rust
use rpc_io::jsonx::{DecodeError, FromJson, Reader};
use rpc_io::{Endpoint, Router};

struct Open<'a> { uri: &'a str }

impl<'de> FromJson<'de> for Open<'de> {
    fn from_json(reader: &mut Reader<'de>) -> Result<Self, DecodeError> {
        let mut uri = None;
        let mut object = reader.read_object()?;
        while let Some(key) = object.next_key()? {
            if key == "uri" {
                object.field(&mut uri)?;
            }
        }
        Ok(Open { uri: object.required(uri, "uri")? })
    }
}

let router = Router::new().request_encoded("open", |_: &mut (), params, _| {
    let open: Open<'_> = params.decode()?; // `uri` borrows from the message
    Ok(open.uri.len())
});
let (tx, rx) = std::sync::mpsc::channel::<String>();
Endpoint::new(tx, router, ()).handle(br#"{"jsonrpc":"2.0","id":1,"method":"open","params":{"uri":"a.rs"}}"#)?;
assert_eq!(rx.try_recv().ok().as_deref(), Some(r#"{"jsonrpc":"2.0","id":1,"result":4}"#));
# Ok::<(), rpc_io::Error>(())
```

jsonx-lib is re-exported as `rpc_io::jsonx`, so a crate on top (an LSP or
MCP server) needs no jsonx-lib dependency of its own and always gets the
version rpc-io was built with.

### MCP 2026-07-28: stateless

MCP's current revision removed the `initialize` handshake: every request
carries its protocol version in `_meta`. 0.3's `Config::mcp()` gated every
request on `initialize`, so a modern client had every request refused, with
`-32002`, a code the revision now forbids. `Config::mcp()` now has no gate,
writes errors for unreadable messages without `id` (MCP's schema has no
`null` id), and refuses requests past `max_in_flight` with `-32603` (MCP asks
new implementations not to use `-32000..=-32019`). Batches stay off and the
cancellation spelling is unchanged. A server whose clients all speak a legacy
revision (2025-11-25 and earlier) takes `Config::mcp_legacy()`, whose gate
now refuses early requests with `-32600`. A dual-era server keeps
`Config::mcp()` and picks each request's semantics itself, as the
specification describes. An error response without `id` from the peer is
read as one under `null` under every config.

### Progress that follows MCP's rules

`Progress::report` refuses a value that does not exceed the last one sent
for the handle and its clones (`Error::ProgressNotIncreasing`), and sends
nothing; the check and the send share a lock, so reports from several
threads reach the wire in increasing order. A `Progress` from
`Context::progress` or `Responder::progress` is bound to its request: once
the request is answered or cancelled, `report` refuses with
`Error::AlreadyAnswered`, checked under the lock the response is written
under, so no report can follow the response on the wire. Reports are encoded
in a per-thread reused buffer instead of being allocated.

### Notifications bound to a request

`Notifier`, from `Responder::notifier` or `Context::notifier`, sends
notifications only while its request is in flight, with the same lock-held
check: the shape of MCP's `subscriptions/listen` stream, requested by mcp-io.

### The 1.0 decisions, made now

- `Request`, `Notification`, and `Response` are `#[non_exhaustive]`, with
  constructors (`Request::new`, `Notification::new`, `Response::new`, `ok`,
  `err`); their fields stay public.
- `ErrorCode(pub i64)` stays a plain, exhaustive newtype: it is the JSON
  integer and nothing more.
- Lenient ids: `Limits::with_lenient_ids(true)` accepts the request ids
  JSON-RPC 2.0 allows and discourages (`null`, fractions, exponents,
  integers outside `i64`) and echoes them back exactly as sent, for generic
  JSON-RPC services. Off by default and in every preset. `Id` gains
  `RawNumber` and `Null` and stays exhaustive: those are every id JSON-RPC
  2.0 allows.

## Security

Repeated envelope members (the jsonx-lib baseline audit's JX-SEC-02: a
reader loop that keeps the last key reads
`{"method":"initialize","method":"shutdown"}` as one method and runs another)
did not affect rpc-io, in 0.3.0 or before: its envelope reader refuses any
repeated `jsonrpc`, `id`, `method`, `params`, `result`, or `error` with
`-32600`. New regression tests pin it, through the gate and in batches, and
pass unchanged on 0.3.0. Under jsonx-lib 0.5, whose readers refuse repeated
keys by default, rpc-io reads envelopes with repeats passed through to its
own check, so the answer stays `-32600` under the request's id, as in 0.3.

## Breaking changes

A pre-1.0 minor release may break; each change has a migration:

- **jsonx-lib 0.5** (from 0.2), whose types are part of this crate's API
  (`Raw::parse` returns a `jsonx_lib::Value`, `Raw::new_with` takes a
  `jsonx_lib::Parser`). Use `rpc_io::jsonx`, or depend on `jsonx-lib = "0.5"`.
- **`Request`, `Notification`, `Response` are `#[non_exhaustive]`.** Build
  them with the constructors; add `..` to struct patterns.
- **`Id` has two more variants**, `RawNumber` and `Null` (produced only with
  lenient ids). Add arms, or `_`, to exhaustive `match`es.
- **`Config::mcp()` has no gate**, omits `id` on errors for unreadable
  messages, and refuses past `max_in_flight` with `-32603`. A server for
  legacy MCP clients only uses `Config::mcp_legacy()`.
- **`Gate::mcp()` refuses with `-32600`**, not `-32002`; `with_code` chooses
  another.
- **`Progress::report` refuses** a value that does not increase
  (`Error::ProgressNotIncreasing`); bound to a request, it refuses once the
  request is over (`Error::AlreadyAnswered`).
- An error response without `id` from the peer is read as an error under
  `null` instead of being dropped as invalid.

## Performance

Measured with the benchmarks in `benches/` (`bench`, and the new `typed`),
on a machine loaded by other work: 0.3.0 and 0.4.0 ran back to back, and the
figures are the range of medians over two rounds (three for
`handle_100k_unparsed`). The README has the full table.

| Benchmark | 0.3.0 | 0.4.0 |
|---|---:|---:|
| `messages/decode_100k_requests` | 2.3 M/s | 2.8-3.0 M/s |
| `messages/decode_batch_1024` | 330-350 µs | 270-300 µs |
| `framing/decode_100k_Newline` | 6.7-7.1 GiB/s | 8.2 GiB/s |
| `typed/progress_100k_reports` | 1.4-1.5 M/s | 9.8-10.2 M/s |
| `endpoint/handle_100k_unparsed` | 1.81-1.97 M/s | 1.67-1.80 M/s |
| `endpoint/handle_100k_requests` (handler parses a `Value`) | 605-685 K/s | 505-580 K/s |
| `typed/handle_100k_request_json` (`FromJson`/`ToJson`) | | 725-845 K/s |
| `typed/handle_100k_serde` | 1.36-1.41 M/s | 1.21-1.41 M/s |

Envelope decoding is faster: rpc-io reads envelopes with jsonx-lib 0.5's
duplicate-key tracking off and checks repeated envelope members itself.
Progress reports no longer allocate. Handlers that parse params are slower,
and the `FromJson` path is slower than `serde_json`. Most of that time is
jsonx-lib 0.5's: its `parse` measures 8-18% slower than 0.2's on these
params and allocates once more per object, for the duplicate tracking its
default policy now does in the reader. Repeated keys inside params stay
refused on purpose, and the cost is reported to jsonx-lib. The endpoint's
own path measured 5-12% lower in these rounds, with the same one allocation
per request as 0.3.0; a harness reusing one endpoint measured the two
versions the same (median 468 ns against 473 ns). 0.3.0's code built on
jsonx-lib 0.5 took about 870 ns, which is what reading envelopes without
duplicate tracking removes.

## The 0.3.0 verification's leftovers

- `docs/API.md` examples are whole programs: no rustdoc-hidden lines for
  GitHub to show.
- The benchmarks were re-measured (above), as ranges.
- The rest were fixed before 0.3.0 shipped (an outstanding request of ours
  no longer keeps a `Server` connection out of idle; the slow-trickle
  server test tolerates a reset on Windows), or stay where the roadmap puts
  them (loom models at v0.9.0).

## What's next

- **0.5.0**: Streamable HTTP, SSE, and WebSocket framings over the owner's
  net crates; Windows named-pipe serving; a shared timer for `Server`.
- **0.9.0**: conformance suites backed by the fuzz corpus; loom models of the
  cancellation races.
- **1.0.0**: the freeze, once lsp-lang and mcp-io run on it (D18).

The `#[rpc]` proc-macro router stays out of scope: a proc-macro needs
`syn`/`quote`, and `Router::request_json` covers typed routing by hand.

## Installation

```toml
[dependencies]
rpc-io = "0.4"

# Framing, messages, and correlation only (no_std, alloc)
rpc-io = { version = "0.4", default-features = false }

# With the integrations
rpc-io = { version = "0.4", features = ["serde", "futures-io", "tracing", "net"] }
```

MSRV: Rust 1.85. Requires jsonx-lib 0.5.
